## Machinery facts this review depends on (established first, cited below)

**M1 — `LoadStr` is ANSI, `LoadStrU8` is UTF-8, and both share the "10000-byte
rotating buffer" shape** (`src/salamdr2.cpp:34`, `:89`). `LoadStr` calls
`LoadString` (= `LoadStringA`, core built without `UNICODE`) so the bytes are
the ACP form of the translated string; `LoadStrU8` calls `LoadStringW` +
`SalWToU8`. For a **pure-ASCII** resource string the two are byte-identical;
they differ only when the translation contains a non-ASCII character.

**M2 — the `Sal*U8` sinks are all-or-nothing and silently fall back**
(`src/common/winlib.cpp:1102-1233`). Every one of `SalSetWindowTextU8`,
`SalSetDlgItemTextU8`, `SalComboAddStringU8`, `SalListBoxAddStringU8`,
`SalInsertMenuItemU8`, `SalListViewSetItemTextU8`, `SalStatusSetTextU8` does:
`SalU8ToWAlloc(text)`; on success → the `W` message; on NULL (**the whole
buffer is not valid WTF-8**) → the raw `A` call. Consequence (this is DC-19):
a buffer that mixes ACP bytes with UTF-8 bytes fails the probe as a *whole*, so
the sink takes the `A` path and the UTF-8 part becomes mojibake — while the
same code in English (ASCII template) passes the probe and renders correctly.
The fallback therefore **hides** the defect from any sink-based guard rule.

**M3 — `CMessageBox` caption and body both go through U8 sinks**
(`src/msgbox.cpp:472` `SalSetWindowTextU8(HWindow, Title)`, `:475`
`SalSetDlgItemTextU8(HWindow, IDS_MSGBOX_TEXT, Text.Get())`), and the
measure/wrap path re-probes the body independently (`:676`
`WCHAR* bodyW = SalU8ToWAlloc(Text.Get())`; `:698` `SetWindowTextW(...)` on the
wrapped wide text, else `:709` `SetDlgItemText(...)` ANSI). Caption and body are
**probed separately**, so a caption may take the `A` path while the body takes
the `W` path (and vice versa) in the same dialog.

**M4 — `CheckText` and the hint label are ANSI-only sinks**
(`src/msgbox.cpp:526` `SetDlgItemText(HWindow, IDS_MSGBOX_HINT, hintLabel)`,
`:547` `SetDlgItemText(HWindow, IDS_MSGBOX_CHECK, CheckText)`, measured with
ANSI `DrawText` at `:746`). Anything UTF-8 placed in `CheckText` is mojibake.

**M5 — button alias labels use a U8 sink** (`src/msgbox.cpp:925`
`SalSetWindowTextU8(hButton, aliasName)`, `:960`
`SalSetWindowTextU8(hButton, LoadStr(btnText[i]))`). Note `:960` feeds a
**`LoadStr` (ANSI)** value to a U8 sink — correct only because of the M2
fallback, and only while the label is a single resource string.

## Part 1 — DC-03 / DC-05 / DC-19: printf compositions with a `LoadStr` format

**Method used.** For every line of `candidates/dc03-05-19-loadstr-compositions.txt`
I resolved (a) the arguments' producers, (b) the sink the composed buffer
reaches (script-assisted, then read by hand), and (c) — where the verdict
depends on a translated word being non-ASCII — the **actual string** in
`translations/<lang>/salamand.slt` for the 8 enabled languages (the resource
id → number map comes from `src/texts.rh2`). Results of (c) are quoted inline
as `non-ASCII in: …`; the 3 disabled languages never make a site defective.

**The defect mechanism in one line** (all of Part 1 rests on it): the sinks in
this codebase probe the **whole buffer**. `LoadStr` template bytes are ACP;
a UTF-8 name/path/`GetErrorText` argument makes the concatenation invalid
UTF-8; the probe fails; the sink silently draws the buffer as ACP; the UTF-8
half becomes mojibake. English (and any language whose particular string is
ASCII) passes the probe and looks right — which is why these survived.

## Part 4 — cross-cutting notes on the message-token queue (`dc06b`)

## Notes

- **N1** `src/fileswn7.cpp:1589-1591` builds one alias-button buffer from
  `LoadStrU8(IDS_CONFIRM_ADDTOARCHIVE_ADD)` **and** `LoadStr(
  IDS_CONFIRM_ADDTOARCHIVE_OVER)`. It works only because `CMessageBox` splits
  the buffer on TAB before the sink (`src/msgbox.cpp:912-918`). Any future
  change that measures or draws the alias buffer as a whole breaks it.
- **N2** `src/dialogs5.cpp:3404` carries the comment "composed with localized
  UTF-8 text (feature 010)" on a buffer whose template is `LoadStr(
  IDS_TASKLISTLINE)` — i.e. ANSI. The comment is wrong; the site is latent
  only because short date/time are ASCII in the shipped locales.
- **N3** `IDS_QUESTION` is loaded as `LoadStr` at 43 caption sites and as
  `LoadStrU8` at one (`src/finddlg2.cpp:1984`). Both work; the inconsistency
  is what makes the DC-18 mechanical check noisy. A one-line rule ("captions
  passed alone may use either; compositions must use `LoadStrU8`") would let
  the guard skip caption-only twins.
- **N4** `src/dialogs5.cpp:107` writes the `CToolbarHeader` through
  `SalSetWindowTextU8` with the comment "localized text is UTF-8 (feature
  010)", but the template `InstalledPluginsText` comes from
  `GetDlgItemText` (`:498`, ANSI). Harmless today (the buffer is homogeneous
  ANSI), but the header re-reads its own text with `GetWindowText`(A) when it
  paints (`src/gui.cpp:2915`), so the pair is only safe while **both** ends
  stay ANSI.
- **N5** A control can legitimately carry two encodings item-by-item when the
  sink probes per item (drive bar `src/toolbar2.cpp:301-310`, menus
  `src/menu3.cpp:940-1054`, `CMenuBar` `src/menubar.cpp:195-203`). This is why
  `src/drivelst.cpp:2015` (ANSI) and `:2021` (UTF-8) coexist correctly, and
  why F-P2-08 was withdrawn. The rule that matters is **per-buffer
  homogeneity**, not per-control.
- **N6** The ANSI chain is only lossless while the process ACP matches the UI
  language. `LoadStr` = `LoadStringA` converts the resource's UTF-16 through
  the ACP, so a Czech UI on an ACP-1252 machine already loses `ř`/`ů` before
  any of the sinks above see the bytes. That is pre-004 behaviour and out of
  scope, but it is the reason "homogeneous ANSI" is a *consistency* verdict,
  not a *correctness* one.
- **N7** Guard gaps this review's findings imply (for P7): (a)
  `mixed-composition` must drop the 14-line `MSGBOX` proximity requirement and
  the `NAME_ARG` identifier heuristic — `GetErrorText`, `NumberToStr`,
  `PrintDiskSize`, `LoadStrU8` are *known* UTF-8 producers and should qualify
  an argument on their own; (b) it must follow a `LoadStr` format into a
  buffer assigned to `MSGBOXEX_PARAMS.Text`, `CWaitWindow::SetText`,
  `CStaticText::SetText`, `Sal*U8` sinks and `COperations` subject; (c)
  `ansi-template-number` must handle the two-step
  `PrintDiskSize(v,…); … sprintf(buf, LoadStr(X), v)`; (d) a new sub-shape:
  an **ANSI template that is not `LoadStr`** — a translated format read back
  with `GetDlgItemText`/`GetWindowText` and used as a `printf` format
  (`src/dialogs5.cpp:327,353`); (e) `UTF8_IDENT` must gain `DLLName`,
  `Version` and the plugin menu-item `Name`.
