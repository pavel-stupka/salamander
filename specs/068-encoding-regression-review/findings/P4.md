### F-P4-01 — the viewer's default character-set conversion is silently lost on every restart when its name is non-ASCII (Kamenické / KOI-8 ČS2)

- Sites: S-B7-P4-001, S-B7-P4-002
- Defect class: **DC-17** (`undefined-encoding-of-cached-string`) — this is
  exactly the class ledger row L17 says was never swept, outside `CPluginData`.
- Failure scenario: **Internal Viewer → Coding menu**, on any system whose
  best-matching conversion directory is `convert\centeuro` (Central-European
  ACP, i.e. the primary Czech/Polish/Hungarian/Slovak install — the shipped
  Czech, Polish, Hungarian, Slovak languages), **any UI language**. The user
  opens a file, picks the coding *"Kamenické - CP1250"* (or *"KOI-8 ČS2 -
  CP1250"*, *"CP1250 - Kamenické"*, *"Kamenické - ASCII"*, *"Kamenické -
  CP852"*, *"CP852 - Kamenické"*, *"CP1250 - KOI-8 ČS2"* — 8 of the ~30 shipped
  conversions) and chooses **Set As Default** (`CM_SETDEFAULT_CODING`). It works
  for the rest of the session. After the next start of Tandem Commander the
  default conversion is **gone**: files open unconverted ("None"), and the
  Coding menu no longer marks the chosen item as the default (the default
  marker moves to the "None" item, `CM_CODING_MIN + 0`). Re-doing "Set As
  Default" never sticks —
  the setting is permanently unable to survive a restart.
- Data path:
  1. `src/codetbl.cpp:155-157` — the conversion **name is copied raw out of
     `convert\centeuro\convert.cfg`**: `memcpy(name, beg, l); name[l] = 0;` — no
     conversion of any kind. That file is **CP1250-encoded** (verified at byte
     level: `Kameni\xe8t\xed`, `KOI-8 \xc8S2`, 13 non-ASCII bytes). So
     `CCodeTablesData::Name` holds **CP1250 bytes**, permanently, for the whole
     process lifetime.
  2. `src/viewer3.cpp:1886` `CodeTables.GetCodeName(CodeType, DefaultConvert, 200)`
     → `src/codetbl.cpp:839` `strcpy(buff, Table->Data[codeType-1]->Name)` —
     `CViewerWindow::DefaultConvert` now holds CP1250 bytes.
  3. `src/viewer3.cpp:3594` `strcpy(Configuration.DefaultConvert, DefaultConvert)`.
  4. `src/mainwnd2.cpp:2001`
     `SetValue(actKey, VIEWER_DEFAULTCONVERT_REG, REG_SZ, Configuration.DefaultConvert, -1)`
     → `src/regwork.cpp:211-216` `SetValueAux` → `src/salamdr6.cpp:2400`
     `SalRegSetValueExW8`. There `SalU8ToW` **fails** (CP1250 bytes are not
     valid WTF-8) and the *transitional ANSI tolerance branch*
     (`salamdr6.cpp:2432-2442`, `MultiByteToWideChar(CP_ACP,…)`) stores the
     value — correctly, as UTF-16 `Kamenické - CP1250`.
  5. `src/mainwnd2.cpp:3638` `GetValue(actKey, VIEWER_DEFAULTCONVERT_REG, …)`
     → `src/regwork.cpp:118` `SalRegQueryValueExW8` returns the value as
     **UTF-8** (`salamdr6.cpp:2352` `SalWToU8`). `Configuration.DefaultConvert`
     is now `Kamenick\xC3\xA9 - CP1250`.
  6. `src/viewer2.cpp:1131` `if (!CodeTables.GetCodeType(DefaultConvert, defCodeType)) defCodeType = 0;`
     → `src/codetbl.cpp:774-808` compares the stored value **byte by byte**
     (`LowerCase[*n] != LowerCase[*c]`) against `Table->Data[i]->Name`, i.e.
     UTF-8 vs CP1250 → no match → `codeType = 0` → `viewer2.cpp:1135-1139`
     `CodeType = 0; UseCodeTable = FALSE;` — the file is shown unconverted.
     Same loss at `src/viewer3.cpp:3273` (`SetMenuDefaultItem` in the Coding
     menu) and at `src/viewer3.cpp:1879` (`CM_RECOGNIZE_CODEPAGE`).
- Evidence:
  - `convert/centeuro/convert.cfg` (raw bytes): `Kameni\xe8t\xed - CP1250=KAME1250.TAB`,
    `KOI-8 \xc8S2 - CP1250=KOI81250.TAB` (+6 more lines).
  - `src/codetbl.cpp:155` `memcpy(name, beg, l);` — no conversion at intake.
  - `src/salamdr6.cpp:2416` `int wlen = SalU8ToW((const char*)lpData, cbData, NULL, 0);`
    … `2432` `{ // transitional tolerance: a not-yet-migrated caller passed ANSI bytes`.
  - `src/codetbl.cpp:795` `if (LowerCase[*n] != LowerCase[*c] || *n == 0) break;`
- Note on generality: the write side is *not* the bug — the facade's ANSI
  tolerance stores the right Unicode. The bug is that the **at-rest encoding is
  UTF-8 while the in-memory table stays CP1250**, so the two can never be
  compared. That is the DC-17 shape verbatim.
- Suggested minimal fix (one line of intent): normalize the conversion name at
  its single intake — `src/codetbl.cpp:155` → `SalLegacyToU8Alloc`-style
  normalization of `name` (the convert.cfg files are legacy ANSI data), making
  `CCodeTablesData::Name` UTF-8 by contract like `CPluginData` after 052; every
  consumer (`GetCodeName`, `GetCodeType`, the Coding menu, the viewer caption)
  then sees one encoding.

### F-P4-02 — a non-ASCII coding name poisons the whole viewer window caption, mojibaking the file name

- Sites: S-B7-P4-003
- Defect class: **DC-19** (`u8-sink-fallback-masks-composition`) + DC-17
- Failure scenario: Internal Viewer, Central-European install (`convert\centeuro`),
  any UI language. The user views a file whose **name contains non-ASCII
  characters** (e.g. `poznámky.txt`) and switches the coding to *"Kamenické -
  CP1250"*. The window caption is composed as `<path> - [<coding name>]`; the
  coding name contributes CP1250 bytes, so the whole caption stops being valid
  UTF-8, `SalU8ToWAlloc` returns NULL, and the code falls back to the ANSI
  `SetWindowText`. The **file name** part — which was correct UTF-8 — is now
  interpreted as CP_ACP: the caption reads `pozn├ímky.txt` (mojibake) instead
  of `poznámky.txt`. Switching back to an ASCII-named coding repairs it.
- Data path: `src/viewer3.cpp:53` `CodeTables.GetCodeName(CodeType, codeName, 200)`
  (CP1250 bytes, see F-P4-01 step 1) → `:59` `sprintf(caption + strlen(caption), " - [%s]", codeName)`
  where `caption` already holds the UTF-8 file name → `:62` `WCHAR* captionW = SalU8ToWAlloc(caption);`
  → NULL → `:69` `SetWindowText(HWindow, caption)` (ANSI).
- Evidence:
  - `src/viewer3.cpp:62-69`
    ```
    WCHAR* captionW = SalU8ToWAlloc(caption); // the title carries a UTF-8 file name (feature 004)
    if (captionW != NULL) { SetWindowTextW(HWindow, captionW); free(captionW); }
    else // not valid UTF-8 (transitional): keep the legacy path
        SetWindowText(HWindow, caption);
    ```
- Suggested minimal fix: same one-line intake normalization as F-P4-01 removes
  this too (the composition then stays UTF-8 end to end).

### F-P4-03 — custom packer/unpacker titles have no defined encoding at rest (the class L17 names)

- Sites: S-B7-P4-004, S-B7-P4-008
- Defect class: **DC-17** — the exact ledger row L17 ("registry-cached translated
  strings outside `CPluginData`, `packers.cpp:734`").
- Failure scenario (the honest one): there is **no mojibake today**, because
  every consumer of a packer title is a tolerant `Sal*U8` sink that falls back
  to the raw `A` call. What *is* broken is the invariant: the same field holds
  three different encodings depending on how it was last written —
  (a) **ACP bytes** when seeded from `LoadStr(IDS_DP_*_E)` on first run or a
  config-version upgrade (`packers.cpp:240,249,262,271`, `:1058,1068`,
  `packac.cpp:999,1007,1033`); the Czech string is non-ASCII —
  `"JAR (Externí Win32, testováno s v1.02)"` (`translations/czech/salamand.slt:1894`);
  (b) **UTF-8** when typed by the user (`edtlbwnd.cpp:542 SalGetWindowTextU8`);
  (c) **UTF-8** for everything reloaded from the registry (the facade's read
  side). Two live consequences:
  1. On an install whose **ACP cannot represent the UI language** (any shipped
     language on an English/Western Windows: Polish, Hungarian, Slovak letters
     outside CP1252), `LoadStr` already substitutes `?`. Because the title is
     then **persisted**, the `?` is baked into the user's registry and survives
     even after the ACP problem goes away — the Pack dialog combo keeps showing
     `"ZIP (Zewn?trzny Win32 ...)"` forever. `LoadStrU8` at those call sites
     would not have that problem.
  2. The tolerance is load-bearing: an ACP title that happens to *parse* as
     UTF-8 (a 3-byte lead + 2 continuation bytes, e.g. CP1250 `ezs`-with-carons
     = `EC 9E 9A`) is taken by the U8 sink and by `SalRegSetValueExW8`'s W
     branch as U+E79A and stored as that. Rare, but the design has no defense.
- Data path: `src/packers.cpp:240` `SetPacker(index, 1, LoadStr(CustomPackers[idx].Title[0]), ...)`
  -> `src/packers.cpp:734` `data->Title = DupStr(title);`
  -> `src/packers.cpp:841` `SetValue(hKey, SALAMANDER_CPU_TITLE, REG_SZ, GetPackerTitle(index), -1)`
  -> `src/salamdr6.cpp:2432` (ANSI tolerance branch) -> registry UTF-16
  -> `src/packers.cpp:934` `SetPacker(index, (int)type, title, ...)` with a UTF-8 `title`
  -> `src/dialogs3.cpp:1861` `SalComboAddStringU8(...)`.
- Suggested minimal fix: `LoadStrU8` at the nine seeding call sites
  (`packers.cpp:240,249,262,271,1058,1068`, `packac.cpp:999,1007,1033`), and
  document `CPackerConfigData::Title` / `CUnpackerConfigData::Title` as UTF-8
  the way 052 documented `CPluginData` (normalize plugin-supplied titles at
  `plugins1.cpp:584/610` with `SalLegacyToU8Alloc` for future non-ASCII plugin
  titles).

### F-P4-04 — the per-drive "remembered directory" is read back from the registry through the ANSI API although it was written UTF-8: a non-ASCII remembered path is lost on every restart

- Sites: S-B7-P4-009
- Defect class: **DC-01** (`ansi-api-on-utf8-path`) + DC-09 — and a straight
  **asymmetric round trip**: the save side uses the facade, the load side a raw
  `RegEnumValueA`.
- Failure scenario: **Main window, drive change** (`Alt+F1`/`Alt+F2` drive menu,
  a Drive-bar button, `Shift+<letter>`), **any UI language, any locale**. The
  user leaves the right panel in `D:\Dokumenty\Ucetnictvi` (with Czech
  diacritics) and exits (Save Configuration on exit is the default). On the
  next start, pressing the `D:` button no longer returns there — the panel
  opens at `D:\`. The per-drive memory is silently and permanently broken for
  every drive whose remembered directory contains a non-ASCII character; it
  works again during the session (the in-memory value is rewritten in UTF-8 by
  `UpdateDefaultDir`) and breaks again on every restart.
- Data path:
  1. `src/mainwnd1.cpp:541,550` `strcpy(row, pathActive)` — `DefaultDir[26][MAX_PATH]`
     is filled from `CFilesWindow::GetPath()`, i.e. **UTF-8** (feature 004).
  2. `src/mainwnd2.cpp:1345` `SetValue(actKey, name, REG_SZ, path, -1)` ->
     `SalRegSetValueExW8` -> correct UTF-16 in the registry.
  3. `src/mainwnd2.cpp:2638` `res = RegEnumValue(actKey, i, name, &nameLen, 0, &type, path, &dataLen);`
     — the core is built without `UNICODE`, so this is **`RegEnumValueA`**: the
     stored UTF-16 is converted to **CP_ACP**.
  4. `src/mainwnd2.cpp:2647` `memmove(DefaultDir[d2 - 'a'], path, dataLen);`
  5. `src/fileswn3.cpp:2749` `ChangePathToDisk(HWindow, DefaultDir[LowerCase[drive] - 'a'], ...)`
     -> `SalPathToWExtAlloc` (`src/common/salpath.cpp`) -> `SalU8ToWAlloc`
     **strict** -> NULL -> `SalFindFirstFile`/`SalCreateFile` return
     `ERROR_INVALID_NAME` (`src/common/salfileio.cpp`, `SalFindFirstFile`) ->
     the path is treated as inaccessible and the panel falls back to the root.
- Evidence:
  - `src/mainwnd2.cpp:2638` (raw `RegEnumValue`, no `W8` facade) vs
    `src/mainwnd2.cpp:1345` (`SetValue` -> facade).
  - `src/common/salfileio.cpp` `SalFindFirstFile`:
    `WCHAR* w = SalPathToWExtAlloc(u8pattern); if (w == NULL) { SetLastError(ERROR_INVALID_NAME); return INVALID_HANDLE_VALUE; }`
  - `src/mainwnd1.cpp:520-552` `UpdateDefaultDir` writes `GetPath()` (UTF-8).
- Suggested minimal fix: replace the `RegEnumValue` loop with 26 explicit
  `GetValue(actKey, name, REG_SZ, ...)` calls (the value names are the single
  letters `A`..`Z`, exactly what the save side writes) — one facade call per
  drive, no enumeration needed.

## Seeds

- **C-j — the 34 uses of the older ANSI wrappers `SalRegQueryValue(Ex)`: CONFIRMED as a
  real (partly) defective set, but not uniformly.** The 34 grep hits break down as:
  6 declarations/definitions/ABI forwarders (dismissed), 2 `REG_BINARY` reads
  (`plugins2.cpp`, harmless), 6 `HKCR` class-identifier reads (`icncache.cpp`,
  ASCII by construction), 1 CLSID text + 1 handler description (`shiconov.cpp`,
  the second latent), 1 icon path (`salamdr1.cpp:2125`, consistent ANSI chain),
  1 `.slg` name (`salmoncl.cpp:141`, ASCII), 2 BIOS diagnostics (`bugreprt.cpp`,
  contract-exempt), 3 network-drive values (`drivelst.cpp:108,116,125`, latent —
  consistently ANSI on both sides of the comparison) and **3 OneDrive values
  (`drivelst.cpp:1503,1533,1537`) that are genuinely defective** (F-P4-05). The
  seed's premise — "the old wrappers are a residue that should have gone to the
  facade" — holds: they are the only registry reads in core that bypass
  `SalRegQueryValueExW8`, and exactly the ones carrying a *path* are broken.
  Two additional raw-ANSI registry **reads** that the seed's grep did not catch
  because they use a different API are the more serious ones:
  `mainwnd2.cpp:2638` `RegEnumValue` (F-P4-04) and `salamdr5.cpp:1305`
  `RegEnumValue` (latent) — a `RegEnumValue`/`RegEnumKeyEx` W8 facade does not
  exist.
- **S5 (persistence side) — custom packer/unpacker titles: CONFIRMED as an
  undefined-encoding field, REFUTED as a *visible* mojibake today.** The field
  holds ACP bytes when seeded from `LoadStr` and UTF-8 once it has been through
  the registry or the user's keyboard (F-P4-03); every consumer is a tolerant
  U8 sink, so on a matching ACP nothing is garbled. What the sweep did find is
  that the feature-010 mitigation is only half a fix: `mainwnd2.cpp:2727-2731`
  **resets** the packer sections to defaults for `ConfigVersion < 105` ("no
  garbled entry may survive the upgrade"), and the reset re-seeds them from
  `LoadStr` — i.e. from the very producer that has no defined encoding. The
  *analogous* field that is not saved by a tolerant sink is the viewer
  conversion name (F-P4-01), which is compared byte-wise.

## Notes

- **N-P4-01** — The two legacy wrappers `SalRegQueryValue`/`SalRegQueryValueEx`
  (`salamdr6.cpp:2220`, `:2248`) exist for the plugin ABI and cannot be removed,
  but nothing marks them as plugin-only. Their doc comment says nothing about
  encoding, while the W8 pair 30 lines below carries a full contract block. A
  one-line "core code must use `SalRegQueryValueExW8`; this ANSI pair is
  retained for the plugin ABI" comment would make the remaining 12 core call
  sites visible to the next reviewer (and to a guard rule).
- **N-P4-02** — `CMainWindow::SetDefaultDirectories` (`mainwnd4.cpp:1041-1063`)
  publishes the per-drive current directories to child processes through the
  hidden `=X:` environment variables using the **ANSI**
  `SetEnvironmentVariable`. The value is `DefaultDir[]`, i.e. UTF-8 during a
  session. There is no `SalSetEnvironmentVariable` facade; the fix would be
  `SetEnvironmentVariableW` on a `SalU8ToWAlloc` result. Low severity (it
  affects a launched tool's drive-relative path resolution, not Tandem
  Commander itself), but it is the same *operational* channel class as F-P4-06.
- **N-P4-03** — `GetUserName` (`drivelst.cpp:88-133`) reads `RemotePath`,
  `UserName` and `ProviderName` with the ANSI wrapper and compares `RemotePath`
  against a `WNetGetConnection` (also ANSI) result. The pair is consistent, so
  the *match* works; the `userName`/`providerBuf` outputs are then used for the
  network-login dialog. This overlaps ledger L05 ("drive-bar volume-label
  acquisition ANSI end-to-end") — the same "consistently ANSI, therefore
  self-consistent, therefore invisible until something in the chain is
  converted" pattern. Worth converting together with L05 rather than piecemeal.
- **N-P4-04** — `IconOverlayDescr` (`shiconov.cpp:465`, `:499`) is a
  third-party, localized description read through the ANSI wrapper. Display
  only. Recording it because the *identity* stored next to it
  (`IconOverlayName` → `Configuration.DisabledCustomIconOverlays`) is a
  registry-persisted, byte-compared list — the exact shape of F-P4-01. It is
  safe today purely because shell overlay handlers register ASCII key names.
- **N-P4-05** (new, attached to L77) — `CHotPathItems::Load` reads the label
  into `char name[MAX_PATH]` (`GetValue(actKey, SALAMANDER_HOTPATHS_NAME, REG_SZ, name, MAX_PATH)`)
  while `CHotPathItems::Save` writes it from `char name[HOTPATHITEM_MAXPATH]`
  (= 4×MAX_PATH; feature 047 stores the *effective label*, which for an unnamed
  hot path is the path text). A hot path longer than 259 bytes therefore loses
  its label on reload — `GetValue` returns `ERROR_MORE_DATA` and `name` stays
  empty. Non-encoding, but the byte-vs-character point of L32 applies again.
- **N-P4-06** (consolidates N-P4-09) — `src/plugins/regedt/fs3.cpp:1016,1025,1036` pass a registry key
  **name/path** to the ANSI `CopyTextToClipboard`; regedt is `on` in
  `plugins.cfg` and registry key names are routinely non-ASCII. Whether this is
  a defect depends on the encoding regedt keeps its names in — P5's call. Listed
  so the DC-06 clipboard sweep is complete: the other plugin callers are
  `ftp/ctrlcon2.cpp:2095,2213`, `ftp/dialogs1.cpp:1364`, `ftp/dialogs8.cpp:2001`,
  `checksum/dialogs.cpp:1190`, `pictview/dialogs.cpp:1701`,
  `dbviewer/renmain.cpp:1330`, `filecomp/viewtext.cpp:324`,
  `filecomp/viewwnd3.cpp:858`.
- **N-P4-07** — `LoadHistory` (`salamdr2.cpp:2579`) is the only persistence path
  in the core that *validates* what it loads (`SalU8ToW(...) == 0` → drop the
  entry). If the DC-17 fields are given a documented encoding, that probe is the
  pattern to copy — it costs one line and turns a silent mojibake into a silent
  reset.
- **N-P4-08** — `mainwnd2.cpp:2727-2731` documents the feature-010 decision to
  **reset** the packer/unpacker sections for `ConfigVersion < 105` rather than
  convert them. The reset path re-seeds titles from ANSI `LoadStr`
  (`packers.cpp:240` …), so the "no garbled entry may survive the upgrade"
  guarantee is only as good as the ACP the reset runs under. See F-P4-03.
