## Notes
- **N-01** (`src/common/salunicode.cpp:357`) — `SalLegacyToU8Alloc`'s "already valid UTF-8" probe is now WTF-8-aware, so a legacy ACP byte string that happens to be valid WTF-8 but not valid UTF-8 is now kept verbatim instead of being converted from CP_ACP. That needs the whole string to decode with an `ED A0..BF 80..BF` run in it — in CP1250 that is `í` + one of `NBSP..ż` + one of the `0x80..0xBF` glyphs. Every ACP string containing a byte in `F5..FF` (`ř`, `ů`, `ý`, `ž` in CP1250) still fails the probe. Theoretical narrowing, no scenario, so a Note.
- **N-02** (`src/salamdr4.cpp:1232`) — asymmetric length in the CP_ACP fallback of `CopyTextToClipboardU8`: the UTF-8 branch now passes `wideLen-1`, the fallback still passes `wideLen`. For a `textLen==-1` caller the fallback would put one extra NUL on the clipboard. Unreachable in a shipped configuration.
- **N-03** (`src/zip.cpp:6565`) — `TestFreeSpace` now composes a UTF-8 body but keeps `messageTitle` as the caller supplied it. Whether that caption can be plugin ANSI text is a P5/P2 question (ledger L16); flagged only because 067 touched this line.
- **N-04** (`src/salamdr6.cpp:2358-2382`) — the registry read side now does one extra `malloc`+`memcpy` per string value; configuration load reads a few hundred values, not a per-item path.
- **N-05** (`src/plugins/mdview/webview.cpp:634-643`) — `CMdUdfJanitorThread::Body` calls `SHFileOperationW` on a thread that never initializes COM. The shell file operation is documented as requiring an initialized apartment; where it fails, the stale `mdview.WebView2` folder simply survives (silent, retried next session), so this is a robustness note rather than a defect.
- **N-06** (`src/plugins/mdview/webview.cpp:600-610`) — `MdUserDataFolder` appends 26 characters to `%LOCALAPPDATA%` inside no length guard; a `CSIDL_LOCAL_APPDATA` near `MAX_PATH` would produce a path WebView2 refuses. Not reachable with a normal profile.
- **N-07** (`src/viewer3.cpp:3133`) — `SalU8ToW(u8, -1, ptr->szText, _countof(ptr->szText))` empties the tooltip instead of truncating when the composed text exceeds 80 UTF-16 units. The realistic worst case (hex offset + grouped decimal offset + template) is ~45 units in the shipped languages, so it is unreachable; and the pre-067 code would have *overrun* `szText` in that case, so this is strictly safer.
- **N-08** (`tools/check_encoding.py:276-287`, for P7) — the new `ansi-template-number` rule matches only when the `NumberToStr`/`PrintDiskSize` call is lexically inside the same printf statement as the `LoadStr(` format. The very common two-statement shape is invisible to it, e.g. `src/dialogs.cpp:947-951` (`PrintDiskSize(num1, …, 4); … sprintf(buf, LoadStr(IDS_PROGDLGSTATUSCOPY), num1, num2);` → `Status->SetText(buf)` at `src/dialogs.cpp:1056`), `src/fileswn8.cpp:1403-1404`, `src/drivelst.cpp:2626-2628`. All three are latent today (mode 0/3/4 units are ASCII and the shipped decimal separators are ASCII), but they are the rule's own defect shape and the guard cannot see them.
- **N-09** (`src/dialogs.cpp:947-1056`) — the Copy/Move progress status line composes an ANSI `LoadStr` template with `PrintDiskSize(…, 4)` output and hands the result to `CStaticText::SetText`. Consistent-ANSI today (the mode-4 number is ASCII on every shipped locale), but it becomes mixed the moment a locale supplies a non-ASCII decimal separator. Belongs to P2/P3's DC-05 sweep; recorded here because 067's guard rule was supposed to cover this shape.
