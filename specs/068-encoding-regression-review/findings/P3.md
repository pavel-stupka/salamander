## Notes — running analysis

### N1 `src/common/salunicode.cpp` — line-level read (complete)

Correctness confirmed:
- `SalWToWtf8Units` (52-96): bounds check `out + seq > bufSize` before every
  write; surrogate-pair recombination correct; lone surrogate falls into the
  3-byte branch (`cp < 0x10000`), i.e. `ED A0 80..ED BF BF` — as the contract
  requires.
- `SalWtf8ToWBytes` (131-202): rejects `0x80..0xC1` (stray continuation +
  overlong `C0/C1`), `0xF5..0xFF`, truncated sequences, bad continuation
  bytes, and the overlong/range cases (`seq==2 && cp<0x80`, `seq==3 &&
  cp<0x800`, `seq==4 && (cp<0x10000 || cp>0x10FFFF)`). The **only** relaxation
  vs. strict UTF-8 is that a 3-byte sequence may decode to `D800..DFFF`.
  Matches B10.1 exactly.
- Terminator/`srcLen` bookkeeping in `SalWToU8Wtf8` (100-126) and
  `SalU8ToWWtf8` (206-230) mirrors the WinAPI convention used by the fast
  paths (count includes the terminator).
- `SalWToU8` (278) reaches the WTF-8 encoder **only** when
  `SalWHasLoneSurrogate` is true, so a plain `ERROR_INSUFFICIENT_BUFFER` on
  valid text still returns 0 — totality holds for the sizing query
  (`buf == NULL`), which is what `SalWToU8Alloc` uses. B10.2 compliant.
- `SalLegacyToU8Alloc` (354): probe is `SalU8ToW(src,-1,NULL,0) > 0`, i.e.
  WTF-8-aware (B10 validity-probe obligation); the `maxBytes` clamp walks back
  over continuation bytes so the result stays well-formed.
- `SalWToACPLossless` (400): `WC_NO_BEST_FIT_CHARS` + `usedDefault` check;
  empties the buffer and returns FALSE on any loss.
- `SalIsASCII`, `SalU8Next`, `SalU8CharCount` cast/mask correctly; the
  `(*s & 0xC0) == 0x80` idiom is sign-safe because sign extension preserves
  bit 7/6 in the masked value.

Observations without a shipped failure scenario yet (candidates for Notes or
Findings once a caller is confirmed):
- `SalU8ToWDisplayAlloc` (688-706) over-allocates by exactly one `WCHAR` when
  `srcLen >= 0`: `SalU8ToWDisplay` already added the terminator to the size it
  reports, then line 696 adds another. Harmless (over-allocation), never
  under-allocation.
- `SalCompareNamesUTF8` (613): on `CompareStringEx` failure the fallback is
  `strcmp(u8a, u8b)` — it ignores the explicit `aLen`/`bLen` and therefore
  reads past a non-terminated slice. Unreachable in practice only if all
  callers pass `-1`; to be checked against `sort.cpp`.
- `SalWtf8ToWBytes` accepts a *pair* of 3-byte surrogate sequences (CESU-8)
  and folds it into one supplementary code point, so `SalWToU8(SalU8ToW(x))`
  is not the identity for CESU-8 input. This is ledger row L28 ("CESU-8
  idempotence not guaranteed"); the contract's law is the other direction
  (`SalU8ToW(SalWToU8(w)) == w`), which does hold.

### N2 `src/common/salfileio.cpp` — `SalConvertFindDataW` intake (DC-14)

`salfileio.cpp:61-71`:
```
    if (nameU8 != NULL &&
        SalWToU8(w->cFileName, -1, nameU8, nameU8Size) == 0 &&
        WideCharToMultiByte(CP_UTF8, 0, w->cFileName, -1, nameU8, nameU8Size, NULL, NULL) == 0)
        nameU8[0] = 0;
```
The lenient last resort is reachable **only** when `SalWToU8` returned 0, and
since 066 `SalWToU8` is total, that means exactly one thing: `nameU8Size` was
too small. But the lenient `WideCharToMultiByte(CP_UTF8, 0, …)` needs the same
number of bytes for the only inputs that differ (a lone surrogate: 3 bytes as
WTF-8 `ED A0 80`, 3 bytes as `U+FFFD` `EF BF BD`), so it fails too and the name
becomes the empty string. Net effect: **the lenient branch cannot bake
`U+FFFD` into a name** — DC-14 does not fire here — but it is also dead code,
and the real failure mode is a silently empty name. See F-P3-03 for the buffer
sizing that decides whether that is reachable.

### N4 `src/common/winlib.cpp:1010-1263` — `CTransferInfo::EditLine` + the `Sal*U8` sinks

Two distinct problems, both mine:

1. **DC-12 — `EM_LIMITTEXT` is set in bytes, applied in characters**
   (`winlib.cpp:1057` wide path, `:1065` legacy path): `bufferSizeInChars` is
   the size of the caller's **narrow UTF-8 buffer in bytes**, but
   `EM_LIMITTEXT` limits the edit control in **UTF-16 units**. The control
   therefore accepts up to `bufferSizeInChars-1` characters, which can need up
   to 3× that many bytes. On `ttDataFromWindow` (:1083) `SalWToU8` then fails

   path and `SalSetWindowTextU8`/`SalSetDlgItemTextU8`/`SalGetWindowTextU8`/
   `SalGetDlgItemTextU8`/`SalComboAddStringU8`/`SalListBoxAddStringU8` all use
   *thunked* messages (`WM_SETTEXT`, `WM_GETTEXT`, `CB_ADDSTRING`,
   `LB_ADDSTRING`); USER32 down-converts them through the ACP when the target
   window is ANSI. Only **two** dialogs and **two** windows in the whole core
   are Unicode (`dialogs3.cpp:394` `CCopyMoveDialog`, `dialogs3.cpp:588`
   `CCopyMoveMoreDialog`, `filesbx1.cpp:25` `CFilesBox`, `fileswn5.cpp:2914`

   (`SB_SETTEXTW`) and `SalInsertMenuItemU8` (`InsertMenuItemW`) are **not**
   affected: those are distinct message/API numbers that USER32 does not
   thunk, so they work on an ANSI dialog. That asymmetry is exactly why the
   052/043 listview fixes worked while the edit/combo ones only half-work.

### N6 Seed C-f — `InitLocales` byte tables (`salamdr1.cpp:936-943`)

```
    for (i = 0; i < 256; i++)
    {
        IsNotAlphaNorNum[i] = !IsCharAlphaNumeric((char)i);
        IsAlpha[i] = IsCharAlpha((char)i);
    }
```
`IsCharAlphaNumericA`/`IsCharAlphaA` classify a byte **in the system ACP**.
Index 0xE8 is `č` in CP1250 → `IsAlpha[0xE8] = TRUE`. But since feature 004 the
strings these tables are applied to are **UTF-8**, where 0xE8 is a 3-byte lead
byte and 0x8D is a continuation byte, so the classification is meaningless for
any non-ASCII character: it depends on what the *ACP* would have made of that
byte, not on what the character is. This is a real DC-15 instance (the class's
second half: "byte tables … are the same assumption"), but it is **not** a
crash or a signed-char bug — it is a wrong-answer bug whose visibility depends
entirely on the consumers. Consumer sweep is in N7.

### N10 `LoadStr` / `LoadStrU8` (`salamdr2.cpp:34-125`)

`LoadStrU8` rotates the same 10000-byte ring as `LoadStr` and resets `act` only
when fewer than **200** bytes remain. But `LoadStr` hands the remaining space to
`LoadString`, which **truncates**, while `LoadStrU8` hands it to `SalWToU8`,
which **fails** (`salamdr2.cpp:105`) — and the caller then gets the literal
string `"ERROR LOADING STRING"` (`:114`). So for any resource string whose UTF-8
form is longer than the free tail of the ring, the two functions degrade
differently: truncation vs. a visible English error string. A `WCHAR wide[2048]`
resource can be up to 6141 UTF-8 bytes; the guaranteed free tail is 200. No
concrete shipped string/ring-state pair proven, so this is recorded as a
**Note**, not a Finding — but it is the DC-09 "degrades differently" shape
inside the machinery itself.

## Findings

### F-P3-01 — `SalU8ToW` conflates "invalid input" with "buffer too small" (DC-20)
- Sites: S-X-P3-002
- Defect class: DC-20 (ledger L08)
- Failure scenario: **Panel auto-refresh, any UI language.** A panel path longer
  than roughly `bufSize/3` UTF-8 bytes — reachable with feature-027 long paths —
  makes `SalU8ToW(path, -1, wPath, _countof(wPath))` return 0 for a *capacity*
  reason. `snooper.cpp:582` reads that 0 as "not convertible" and returns, so
  `FindFirstChangeNotificationW` is never armed: the panel silently stops
  auto-refreshing and shows stale content until a manual refresh — the exact
  symptom feature 058 fixed for a different cause.
- Data path: `src/common/salunicode.cpp:245-253` (single `0` return for both
  causes) → `src/snooper.cpp:582`, `:731`, `:768`.
- Evidence: `salunicode.cpp:247` `if (res == 0 && srcLen != 0)` routes to the
  WTF-8 fallback; `SalWtf8ToWBytes` distinguishes `-2` (too small) from `-1`
  (malformed) at `:182`/`:192` vs `:162,169,177`, but `SalU8ToWWtf8`
  (`:210-215`) collapses both into `return 0`.
- Note: the buffer is **not** indeterminate — every failure path writes
  `buf[0] = 0` — so L08's "indeterminate buffer" wording is stale; the live
  defect is that the caller cannot distinguish, so it either skips the
  operation or uses an empty string.
- Suggested minimal fix: propagate the distinction (a second return value or a
  distinct negative code); the WTF-8 layer already computes it.

### F-P3-02 — `srcLen == 0` is reported as conversion failure (DC-20)
- Sites: S-X-P3-003
- Defect class: DC-20
- Failure scenario: any caller converting a computed slice whose length can
  legitimately be zero takes its error branch. The one reachable instance today
  is benign — `stswnd.cpp:704` `GetItemText` with `item->Chars == 0` falls
  through to `SalWToU8Alloc(..., 0)` → `NULL` → empty buffer, which is the right
  answer anyway — so this is raised as a **latent** trap for future callers, not
  a live user-visible defect.
- Data path: `salunicode.cpp:247` (`srcLen != 0` guard) and `:288`
  (`SalWHasLoneSurrogate(src, 0)` is FALSE) → both fall to `return 0` at
  `:270` / `:309`.
- Evidence: `salunicode.cpp:247`, `:288`, `:307-309`.

### F-P3-03 — the file facade fails operations on ANSI-producer paths instead of falling back (DC-09)
- Sites: S-X-P3-004
- Defect class: DC-09
- Failure scenario: **any operation whose path comes from a not-yet-migrated
  ANSI producer** — a legacy plugin's `char*` path, a configuration value
  written by a pre-004 build through a non-facade write, `LoadStr`-derived text.
  `SalPathToWExtAlloc` returns NULL for such bytes and every facade turns that
  into `ERROR_INVALID_NAME` ("The filename, directory name, or volume label
  syntax is incorrect"), whereas the pre-004 ANSI code operated on those exact
  bytes successfully. Contract B7 requires the *opposite* degradation for the
  icon pipeline ("legacy CP_ACP/ANSI fallback, never fail the operation
  outright"), so the two contracts currently disagree and nothing documents it.
- Data path: `src/common/salpath.cpp:261-263` (`SalU8ToWAlloc` → NULL) →
  `salfileio.cpp:29-33` (`SalFindFirstFile`), `:84-88` (`SalCreateFile`),
  `:231-238` (`SalPathOp` → `SalDeleteFile`/`SalRemoveDirectory`), `:299-311`
  (`SalMoveFileEx`), `:318-330` (`SalCopyFile`), `:381-389`
  (`SalGetFileAttributes`), `:392-402` (`SalSetFileAttributes`), and the
  security/encrypt wrappers.
- Evidence: `salpath.cpp:261-263`
  `WCHAR* w = SalU8ToWAlloc(u8path, -1); if (w == NULL) return NULL;`
  plus the identical `SetLastError(ERROR_INVALID_NAME)` block in each facade.
- Note: whether this is a defect or the intended hard contract is a scope
  decision (FR-012); raised because the behaviour is undocumented and
  inconsistent with B7.

### F-P3-04 — `EM_LIMITTEXT` is set in bytes but enforced in characters; overflow silently degrades to a CP_ACP read (DC-12 + DC-09)
- Sites: S-X-P3-005
- Defect class: DC-12 (measure/clamp in bytes) with a DC-09 failure branch
- Failure scenario: **any `CTransferInfo::EditLine` edit field, any ACP.** The
  control is limited to `bufferSizeInChars-1` *characters*; the caller's buffer
  holds that many *bytes*. Typing ~150 accented characters into a
  `char buf[MAX_PATH]` field — the filter/mask field (`dialogs3.cpp:280`), the
  Compare-Directories name fields (`dialogs2.cpp:1235-1236`), the title-bar
  prefix (`dialogs5.cpp:2741`), the view/hex mask lists
  (`dialogs4.cpp:1661-1713`) — makes the OK round trip take the legacy branch:
  `SalWToU8` fails on capacity and `WM_GETTEXT` (ANSI) writes **CP1250 bytes**
  into a buffer the rest of the program treats as UTF-8. The value is then

### F-P3-09 — Find → Delete never takes the wide shell path for an all-ASCII selection (off-by-one)
- Sites: S-X-P3-015
- Defect class: DC-20 (capacity failure indistinguishable from "invalid UTF-8")
- Status: **Note-level** — no user-visible failure could be constructed (see
  below), but the code does not do what its comment says.
- Mechanism: `finddlg2.cpp:169-174` allocates `listSize` WCHARs and calls
  `SalU8ToW(list, (int)listSize, listW, (int)listSize)`. `listSize` is the exact
  byte size of the double-NUL list. For an **all-ASCII** selection the strict
  conversion produces exactly `listSize` units, and `SalU8ToW` then hits
  `if (res >= bufSize) { buf[0] = 0; return 0; }` (`salunicode.cpp:259-263`)
  because it wants room for one more terminator. The caller reads that 0 as
  "not valid UTF-8 (transitional)", frees `listW` and falls back to
  `SHFileOperationA`. So the wide path runs **only** when the selection
  contains at least one multi-byte character.
- Why no scenario: `SHFileOperation` (A and W alike) is MAX_PATH-bound, and for
  ASCII input the A call is equivalent, so the outcome is identical today.
- Contrast: `fileswn8.cpp:133-141` does the same job correctly
  (`wchars = SalU8ToW(..., NULL, 0)`, `malloc((wchars+1)*sizeof(WCHAR))`,
  `fromW[wchars] = 0`).
