## US2 — Diagnosis of the reported location (SC-005, FR-006) — 2026-08-18

**Question**: Explorer showed the blue sync arrows on
`E:\Simopt, s.r.o\HSČR - Dokumenty\Schůzky\2026_08_19` for hours; Tandem
Commander showed nothing. Is OneDrive stuck, and where does the state live?

**Channel determination** (re-runnable probes in research.md R1):

- All seven registered OneDrive overlay handlers (`IsMemberOf`, called from an
  external process exactly as the product calls them) returned **S_FALSE** for
  the folder → the arrows do NOT come from the overlay-handler channel. That
  is why neither Altap Salamander nor Tandem Commander ever showed them on
  folders.
- The shell property **`PKEY_StorageProviderState`** returned **10 =
  `STORAGEPROVIDERSTATE_PENDING_UNSPECIFIED`** for the folder, **4 =
  `PENDING_UPLOAD`** for the document inside, and **3 = `PINNED`** for a
  synced control sibling — matching Explorer's "Stav dostupnosti" column
  ("Čekající synchronizace" vs. "Vždy k dispozici na tomto zařízení").
  propkey.h documents this property as *"Property for the cloud file state
  icon."*
- The pending file (state 4) **was** claimed by a handler (OneDrive5, whose
  icon is the blue arrows) — files in active pending states already badge
  correctly since feature 058; only property-only states (the folder's 10)
  were invisible.

**Stall verdict**: the pending state was **provider-real** — OneDrive's own
store reported a pending upload for hours after the document's creation
(9:20 → mid-afternoon, OneDrive processes running since 7:53). During the
analysis session the queue drained on its own and every item moved to the
PINNED family; Explorer's arrows were truthful the whole time.

**User guidance for future stalls**: check the OneDrive activity center
(tray icon) for the affected file; close the application holding the
document (Word keeps `.docx` files locked, which defers the upload);
pause/resume syncing from the tray menu. The file manager — Explorer or
Tandem Commander — only mirrors the provider's state.

## Implementation notes (2026-08-18)

- Fix per plan: `PKEY_StorageProviderState` fallback in
  `CShellIconOverlays::GetIconOverlayIndex` + synthetic overlay entry
  `TandemCloudSyncPending` (icon `src/res/syncpend.ico`, generated by
  `tools/brand/gen_overlay_syncpend.py`) + per-listing sync-root gate
  (`CfGetSyncRootInfoByPath`, cldapi.dll loaded dynamically).
- `cfapi.h` cannot be included at the project's `_WIN32_WINNT=0x0601` level
  (NTDDI-guarded, depends on newer base types); the two needed ABI-stable
  declarations are mirrored locally in `shiconov.cpp`.
- **Latent upstream bug found & fixed while integrating**: the first build
  crashed at startup (RTC "local variable used before initialization",
  captured in the product's own bug report
  `4206B25030D8CE40-NC012X64-260818-110214.TXT`):
  `GetIconOverlayIndexAuxAux` read an uninitialized `HRESULT res` whenever a
  reader slot was NULL — previously near-unreachable, made constant by the
  synthetic entry's NULL slot. Fixed by initializing `res = S_FALSE` and by
  skipping synthetic entries in the handler loop outright.
