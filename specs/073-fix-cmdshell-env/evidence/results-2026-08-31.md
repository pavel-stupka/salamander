Measured 2026-08-31 on the reporting machine while writing the spec. Secrets
and full variable dumps are deliberately not recorded here — only counts,
names and the values that matter. Every script in this folder reruns the
measurement; none of them presses a key in the running application, so the
one thing they cannot observe is the actual window `Num /` opens (User
Story 2 collects that from the reporter).

## V2 / V3 — the two launch paths (`diag.ps1` + `dumpenv.cmd`)

A launcher process (96 variables — a Claude Code session inside Windows
Terminal, so richer than Explorer's 48) set `TC073_MARKER=from-launcher` and
started `cmd /c dumpenv.cmd <name>`:

| Launch | How | Variables | Marker | `USERPROFILE` | Differences vs the launcher |
|--------|-----|-----------|--------|---------------|-----------------------------|
| `direct` | `CreateProcess` child, no environment block, working directory set — the Command Prompt preset's way | 96 | present | `C:\Users\pavel` | none |
| `wt` | `wt.exe -d . cmd.exe /c …` through the App Execution Alias — the Windows Terminal preset's way | 96 | **present** | `C:\Users\pavel` | `WT_SESSION`, `WT_PROFILE_ID` only |
| `explorer` | `Shell.Application.ShellExecute` from the same launcher | 96 | present | `C:\Users\pavel` | none — note: this COM call ran in-process, so it is **not** an Explorer-environment reference; Explorer's real environment was read directly in V4 instead |

Conclusion: Windows Terminal 1.24 forwards the launcher's environment into
the tab it creates even though the tab's shell is not the launcher's child
(the running Windows Terminal process, started earlier by Explorer, hosted
the tab — no new `WindowsTerminal.exe` appeared). `whoami` = `pavel` and the
working directory = the launcher's in all three.

## V4 — startup regeneration inside Explorer's exact environment (`regen.ps1` + `regen-child.ps1` + `penv-lib.ps1`)

`regen.ps1` reads Explorer's environment block from the running Explorer
(PEB → ProcessParameters → Environment), starts a helper with **exactly**
that environment plus `TC073_MARKER=inherited-only`, and the helper makes the
same shell32 `RegenerateUserEnvironment(&prev, TRUE)` call the application
makes at startup (and on every environment-change notification), then diffs
before/after.

| Measure | Result |
|---------|--------|
| Call | returned TRUE |
| Variables | 49 → 45 |
| Dropped (the application puts these back) | `EFC_14436_1592913036`, `EFC_14436_4126798990` (Explorer-internal), `PSExecutionPolicyPreference` (the helper's own), `TC073_MARKER` |
| Added | none |
| Changed — **artifact, see below** | `PATHEXT` lost `.CPL`; `PSModulePath` lost the leading `C:\Users\pavel\Documents\WindowsPowerShell\Modules;` |
| Unchanged | `PATH` (same entries, same order), `USERPROFILE`, `HOMEDRIVE`, `HOMEPATH`, `APPDATA`, `LOCALAPPDATA`, `TEMP`, `TMP`, `USERNAME`, `COMSPEC`, `OneDrive` |

**Correction (V6, same day)**: the two "changes" were the helper's own doing.
Explorer's `PATHEXT` is `.COM;.EXE;.BAT;.CMD;.VBS;.VBE;.JS;.JSE;.WSF;.WSH;.MSC;.PY;.PYW`
and its `PSModulePath` has no Documents entry — both exactly the `HKLM`
registry values. The helper is Windows PowerShell 5.1, which appends `.CPL`
to `PATHEXT` and prepends its user module folder to `PSModulePath` in its own
process before the script's "before" snapshot ran; the regeneration merely
put the registry values back. Conclusion: on this machine the startup
regeneration changes **nothing** Explorer had.

## V5 — identity

`Win32_Process.GetOwner` of the running application: `PAVEL-PC-5950X\pavel`;
parent `explorer.exe`. The installer's `[Run]` entry is `postinstall
skipifsilent`, so a winget (silent) upgrade never launches the application;
an interactive install launches it as the original user. Not the cause of
elevation or identity change here.

  the common factor; every program Tandem Commander starts is affected.
- With V6 showing the environment identical to Explorer's, a failure from

  directory, the per-drive current-directory entries the launches set, the
  program actually started, or the shell — the process-tree capture below
  records all of them.

## Capturing the failing state (the reporter, at the next occurrence)

1. Start Tandem Commander the usual way (Start menu / taskbar / shortcut).
2. Trigger the failure: `Enter` on the project's `.bat` (or `Num /` and
   `npm run dev`). Leave the window it opened **open**.
3. In **Windows Explorer** (not Tandem Commander, not a terminal) open this
   folder and double-click `capture.cmd`. It runs `penv.ps1` and
   `treeenv.ps1` and records its own — Explorer-started, therefore working —
   Command Prompt as the reference (`whoami`, `where node`, `where npm`,
   `set`), writing `tc-live-<stamp>.txt`, `tc-tree-<stamp>.txt` and
   `ref-explorer-<stamp>.txt` next to itself. System tools are called by
   full path because Git for Windows' `find`/`whoami` shadow them on PATH.
4. Optional, from the failing window itself: `where node` and `where npm`
   (the environment of that window is already in `tc-tree-*.txt`).
5. The files contain no secrets (names containing KEY/TOKEN/SECRET/PASS are
   masked) — read them once before committing.

## Rerunning

```powershell
# from this folder, Windows PowerShell 5.1
.\diag.ps1     # V2/V3: writes env-direct.txt / env-wt.txt / env-explorer.txt next to the script (gitignored - full dumps)
.\penv.ps1     # live environment of explorer.exe and tandemcommander.exe (must be running) + diff
.\treeenv.ps1  # process tree under tandemcommander.exe: cmdline, cwd, env diff vs Explorer per process
.\regen.ps1    # V4: regeneration inside Explorer's exact environment (note the PowerShell artifact above)
```

`diag.ps1` opens one Windows Terminal tab for a fraction of a second. All
scripts are read-only.
